# 産業機器故障予測モデル：ベイズロジスティック回帰による解釈可能な予知保全 AI

> **TL;DR** — UCI/Kaggle の AI4I 2020 Predictive Maintenance Dataset（10,000 件）を用い、
> **5 種類の故障モード（TWF / HDF / PWF / OSF / RNF）を個別にベイズロジスティック回帰でモデル化**し、
> 故障モード別の確率を OR 結合して総合故障確率を算出する解釈可能フレームワークを Python + PyMC + NumPyro で実装。
> 5-fold 層化 CV で **総合故障の AUC 0.979 / AP 0.837 / F1 0.812 (TP=260, FN=79, FP=41, TN=9620)** を達成。
> 実務的解釈としては、339件の真の故障のうち 260件（77%）を事前に検出でき、警告を発した301件のうち 86% が実際に故障する。全体に対する誤警報率は 41/9661 = 0.42% と十分低く、運用上許容できる水準である。
> 各係数の **95% HDI（最高密度区間）** によって「どの物理量がどれだけリスクに効いているか」を統計的に説明可能とし、
> 製造業の **予知保全 AI** としての運用フローを設計した。

## 1. 背景：なぜこの課題を選んだか

製造業の現場では、設備故障による予期せぬダウンタイムが**生産ロス・納期遅延・修理コスト**の三重苦をもたらす。一方で、まだ壊れていない設備を定期的に交換する「時間基準保全」も**過剰メンテナンス**としてコストを押し上げる。

そこで、**センサーデータから「壊れそうな設備」だけを事前に特定する**予知保全（Predictive Maintenance）AI が求められている。ただし産業現場では、

- 「なぜこの設備に故障警告が出たのか」を**現場エンジニアが理解できる**こと
- 故障警告の**不確実性**（=「どれくらい自信を持って言っているか」）が明示されること
- 故障モードごとに**異なる対処法**（工具交換 vs 冷却系点検 vs 電源系点検）を提示できること

が運用上必須となる。これらの要件を満たすため、本プロジェクトではブラックボックスな深層学習ではなく、**ベイズ統計に基づくロジスティック回帰**を採用した。

> 💡 **本プロジェクトの問い**：
> 「故障モードごとに別々の確率モデルを構築し、それぞれの **95% HDI と MCMC 診断**を提示することで、産業現場で『なぜこの警告か』を即答できる予知保全 AI を作れるか？」

## 2. データ

- **Source**: [UCI / Kaggle — AI4I 2020 Predictive Maintenance Dataset](https://www.kaggle.com/datasets/stephanmatzka/predictive-maintenance-dataset-ai4i-2020)
- **Samples**: 10,000 件（シミュレーションベースの合成データ）
- **Target**: `Machine failure`（全故障の OR）と、5 つの独立した故障モード

| 故障モード | 内容                                | 陽性数 | 発生率 |
| ---------- | ----------------------------------- | -----: | ----: |
| **TWF**    | Tool Wear Failure（工具摩耗故障）   |     46 | 0.46% |
| **HDF**    | Heat Dissipation Failure（放熱不良）|    115 | 1.15% |
| **PWF**    | Power Failure（電源故障）           |     95 | 0.95% |
| **OSF**    | Overstrain Failure（過負荷故障）    |     98 | 0.98% |
| **RNF**    | Random Failure（ランダム故障）      |     19 | 0.19% |
| **合計**   | Machine failure                     |    339 | 3.39% |

クラスは**強くインバランス**（全体で 3.39%、最小 RNF は 0.19%）。

### 特徴量エンジニアリング

ドメイン知識に基づき、生センサー値に加えて以下の派生特徴量を作成した。

| 特徴量               | 定義                                                       | 想定故障モード |
| -------------------- | ---------------------------------------------------------- | -------------- |
| `TempDiff`           | プロセス温度 − 空気温度                                    | HDF            |
| `Power`              | トルク × 回転数 × 2π / 60（軸出力 [W]）                    | PWF            |
| `PowerDev`           | `\|Power − 6250\|`（定格 6250W からの絶対偏差）            | PWF            |
| `WearTorque`         | 工具摩耗 × トルク                                          | OSF            |
| `WearTorque_{L,M,H}` | `WearTorque` × 製品タイプ One-Hot（Low / Medium / High）   | OSF            |
| `TempDiff_x_rpm`     | **中心化済み**TempDiff × 中心化済み回転数（共線性回避）    | HDF（交互作用）|

実装: ノートブック内 `load_and_prepare()` 関数

## 3. 手法：なぜベイズロジスティック回帰を選んだか

### 3.1 モデル選定ロジック

| 選択肢                       | 採用 | 理由                                                                |
| ---------------------------- | :--: | ------------------------------------------------------------------- |
| LightGBM / XGBoost           |  ❌  | 高精度だが「なぜ警告したか」の現場説明が困難、不確実性も出ない      |
| 通常のロジスティック回帰     |  ❌  | 点推定のみで、係数の信頼区間や事前知識の組み込みが困難              |
| **ベイズロジスティック回帰** |  ✅  | 係数の **95% HDI**、ドメイン事前分布、MCMC 診断を一括で提供できる    |
| ベイズ階層モデル             |  △  | 設備個体差まで考慮できるが、本データセットには個体 ID がないため不採用 |

### 3.2 モデル定式化 — 「1 故障モード = 1 モデル」分離設計

各故障モード（TWF/HDF/PWF/OSF）について、それぞれ物理的に意味のある特徴量だけを使うベイズロジスティック回帰を独立に推定する。

```python
# 例：HDF（放熱不良）のモデル
intercept ~ Normal(-5.0, 2.0)              # 故障は希少 → 切片の事前は負側に
beta      ~ Normal(prior_mean, prior_sd)   # 物理的方向性を事前に注入
P(HDF=1)  = sigmoid(intercept + X @ beta)
```

故障モード別の特徴量と**事前分布の方向性**は以下のとおり。

| 故障モード | 特徴量                                   | 事前平均（係数）           | 物理的根拠                                |
| ---------- | ---------------------------------------- | -------------------------- | ----------------------------------------- |
| TWF        | Tool wear [min]                          | +3.0                       | 摩耗が増えるほど故障リスクが上がる        |
| HDF        | TempDiff, rpm, TempDiff×rpm              | −3.0, −3.0, **+2.0**       | 温度差が小さい＋低速回転で放熱不足        |
| PWF        | PowerDev                                 | +3.0                       | 定格出力からの逸脱が大きいほど故障        |
| OSF        | WearTorque × {TypeL, TypeM, TypeH}       | +4.0, +3.0, +2.0           | タイプ別の許容トルク × 摩耗閾値の違い     |
| RNF        | （特徴量なし、切片のみ）                 | Beta(1, 1) 一様事前         | ランダム故障は説明変数で説明できない      |

最後に、5 故障モードの確率を **OR 結合**して総合故障確率を算出する:

```
P(Machine failure) = 1 − ∏(1 − P(故障モードᵢ))
```

実装: ノートブック内 `fit_bayes_logreg()`, `cross_validate_target()`, `main()`

### 3.3 サンプラー設定と検証戦略

| 項目                   | 設定                                              |
| ---------------------- | ------------------------------------------------- |
| バックエンド           | **NumPyro**（JAX ベース、PyMC 純正より高速）       |
| MCMC 設定              | `draws=2000, tune=2000, chains=4, target_accept=0.95` |
| 検証                   | **層化 5-fold CV**（クラス不均衡対応）             |
| 指標                   | AUC / AP（Average Precision）/ Brier Score        |
| しきい値               | **F1 最適化**で OOF 予測から自動決定               |
| 収束診断               | R̂ < 1.01, ESS > 400 を必須                        |

## 5. 考察：単純な数値以上に重要な "故障モード分離"の意味

### 5.1 なぜ「1 モデルで全故障を予測」しなかったのか

多くの予知保全モデルは「故障 / 非故障」の 2 値分類を**全特徴量を放り込んだ単一モデル**で解く。しかし本データセットには 5 つの**物理的に独立した故障メカニズム**があり、それぞれ効く変数が違う。

たとえば「工具摩耗」と「過負荷」を 1 つのモデルに混ぜると、

- 「工具がまだ新しいのに高トルクが出ている」状況での過負荷リスクが、摩耗ベースのシグナルに薄められる
- 「どの物理現象で壊れそうか」が出力からわからず、**現場が点検箇所を絞れない**

という問題が起きる。本プロジェクトでは故障モードごとにモデルを分け、最後に確率を OR 結合することで、

- 各モデルの**係数の符号と HDI**が物理的に解釈可能
- 警告時に「これは HDF（放熱不良）由来のリスクです」と**故障モードを名指しできる**

ことを実現した。

### 5.2 RNF（ランダム故障）の AUC 0.5 は「失敗」ではなく「正しい結論」

RNF はデータセット定義上「**全プロセスに 0.1% の確率でランダムに発生する**」故障である。つまり**いかなる特徴量からも予測不可能**であることが理論的に保証されている。

このモデルでは RNF に対しては切片のみのベータ-ベルヌーイモデルを当て、AUC ≈ 0.5（ランダム予測と同等）という結果を得た。これは

| 言えること                                                | 言えないこと                            |
| --------------------------------------------------------- | --------------------------------------- |
| 「データに含まれる情報の上限を正しく見抜いている」        | 「モデルが弱い」「データが足りない」    |

ということ。**「AI が頑張れば AUC が上がるはず」という素朴な期待**を、ベイズ的な不確実性定量化によって冷静に否定できた点は、実務上重要である（無理な精度向上を約束しない判断ができる）。

### 5.3 TWF の AP が低い理由 — 「単一特徴量モデル」の限界

TWF の AUC は 0.972 と高いが、AP は 0.141 と低い。これは陽性数がたった 46 件しかなく、PR カーブが横軸全域で precision が低くなりやすいためである。

実運用では、TWF だけを単独でアラートに使うのは難しい。**総合 Machine failure 確率（OR 結合）を主要な意思決定指標として使い、故障モード別の確率は「点検時の参考情報」として現場に提示する**運用が現実的である。

### 5.4 「95% HDI で説明する」というベイズの強み

各係数の事後分布から、たとえば HDF モデルで以下のような言明が可能になる:

> 「TempDiff × rpm の交互作用係数は 95% HDI が [+1.2, +2.8] と完全に正側にあり、
> **温度差が小さく回転数も低いという条件が同時に成立したとき、放熱不良リスクが統計的に有意に上昇する**」

これは点推定だけのロジスティック回帰では出せない**意思決定者向けの説明**であり、産業現場で「この警告を信じてラインを止めるべきか」を判断する材料になる。

### 5.5 結論：このモデルで言えること・言えないこと

| 言えること                                                       | 言えないこと                                            |
| ---------------------------------------------------------------- | ------------------------------------------------------- |
| 物理メカニズムが明確な故障モード（PWF/OSF/HDF）の高精度予測       | ランダム故障（RNF）の事前予測                            |
| 警告時の**故障モード名と寄与特徴量の根拠**                       | 個別設備の経年変化や個体差（データに ID がないため）    |
| 95% HDI による**統計的に正しい不確実性**                         | 因果効果（観察データであり介入実験ではないため）        |

## 6. 実運用への提案：階層的アラート設計

このモデルを実際の製造ラインに組み込む場合、以下のような**故障モード階層型のアラート運用**を提案する。

```
[センサーデータ (温度/トルク/回転数/工具摩耗/タイプ)]
   │
   ▼
[① 5 故障モード別 ベイズロジスティック回帰]   ← 本プロジェクト
   │   ・各モードごとに P(故障) と 95% HDI を計算
   │   ・モード別最適しきい値で 2 値判定
   ▼
[② OR 結合による総合故障確率 P(Machine failure)]
   │   ・しきい値 0.378 で総合アラート判定
   │   ・F1 = 0.812 (Precision 0.864 / Recall 0.767)
   ▼
[③ アラート時の自動メッセージ生成]
   │   "設備 X に故障リスク (P=0.62)。
   │    寄与: HDF=0.55 (放熱不良), OSF=0.12 (過負荷)。
   │    推奨点検: 冷却系 → 工具摩耗の順。"
   ▼
[④ 現場エンジニアによる確認・処置]
   │   ・故障モード別の点検手順に従う
   │   ・処置結果をフィードバックして事前分布を更新
```

> 💡 **重要な設計思想**：
> 「故障する / しない」の 2 値ではなく、「**どの物理メカニズムでどれくらい確からしく壊れそうか**」を出力すること。
> これにより、現場は「とりあえず全部点検」から「**最も疑わしい系統だけ最短で点検**」に変わり、ダウンタイムと点検工数を同時に削減できる。

事前分布をベイズ更新で逐次改善できる構造にしてあるため、運用しながら**現場の実故障データを取り込んで自動で賢くなる**フィードバックループも構築可能である。

6. 総合 Machine failure 確率の OR 結合と最適しきい値探索
7. **MCMC 診断**（R̂ / ESS / トレース / フォレスト / 自己相関プロット）
8. 全結果を CSV と PNG で Drive に永続保存
